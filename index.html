Task 1: Drawing Single-Color Triangles

Rasterizing a triangle means determining the pixels that lie within it. First, vertices are put in a consistent order so that clockwise and counter-clockwise triangles are handled the same way. Next, select the set of pixels that lie within the triangle's bounding box, which is an area determined by the vertex positions. This limits the scope because it is impossible for any pixels outside the bounding box to be covered by the triangle. Each pixel within this box is then sampled using its center point and checked for whether that point is inside the triangle. A point is considered inside the triangle if it lies on the inner side of all three edges. Points that are exactly on an edge are considered to be inside the triangle.

Our implementation first computes the triangle's bounding box from the smallest and largest x/y coordinates of its vertices. It then loops over every pixel in that box, tests whether the pixel's center lies on the inner side of all three edges, and fills the pixel with the triangle's color if it does. This algorithm is not worse than one that checks each sample within the bounding box, because checking each sample within the bounding box is exactly what our implementation does, with a constant amount of work per pixel.

Task 2: Antialiasing by Supersampling

The main data structure is the sample buffer, which is a std::vector<Color> that stores a floating-point color for each sample. Each pixel's samples are stored next to each other, so when pixels are laid out row by row, a pixel's samples form one contiguous block. The buffer holds width * height * sample_rate samples. We resize it when the window size or sample rate changes and clear it to white before drawing.

For triangles, we kept Task 1's algorithm with the supersampling modifications. Instead of running the tests on just one point in each pixel, we tested on sub-pixel sample points within each pixel, at the centers of a sqrt(sample_rate) × sqrt(sample_rate) grid. Each covered sample gets written into the sample buffer with the triangle's color. Points and lines fill all samples of each pixel they cover. After drawing, we average each pixel's samples and convert the result to 8 bits per RGB channel in the framebuffer.

Supersampling is useful because sampling once per pixel creates jagged edges and makes thin shapes break apart as pixels are only classified as fully colored or not colored at all. Supersampling allows partial coverage, so pixels along an edge can get blended colors. That smooths the edges and keeps thin shapes connected. As a result, at sampling rate 1, the tip of the skinny magenta triangle breaks into disconnected pieces, because it's thinner than a pixel and most pixel centers miss it. At rate 4, more of the tip gets picked up, and partly covered pixels show lighter shades of magenta, so it starts to read as a contiguous line. This continues with greater sampling rates. At rate 16, the tip fades out smoothly because we can represent many more levels of partial coverage.

Task 4: Barycentric coordinates

Barycentric coordinates represent a point inside a triangle using three weights, one for each vertex. Each vertex carries a color. The weights sum to 1 and vary linearly across the triangle, reaching 1 at their vertex and 0 on the opposite edge. For each sample in the triangle, we calculate these weights and use them to interpolate the vertex colors. In the triangle below, the vertices are red, green, and blue, so the colors blend smoothly toward a roughly equal mixture near the center.

Task 5: "Pixel sampling" for texture mapping

Pixel sampling is a process used to determine what color a particular coordinate in texture space should be. For implementation, we first calculate the barycentric coordinates, then we use those weights to interpolate the sample's UV (texture) coordinates from the triangle's vertex UV coordinates. These are stored in a struct along with the sampling modes.

For nearest-neighbor sampling, we use mipmap level 0, the full-resolution texture, for this task. Then we convert our UV coordinate into texel space by multiplying by the texture's width and height. We floor the texel-space coordinates to select the texel containing the point, whose center is nearest, keeping the indices within the texture bounds. This is simple and cheap, however, can produce blocky results, since only a single texel contributes to each sample.

For bilinear sampling, we convert into the same texel space and shift the coordinates by -0.5 to line up with texel centers. We then floor the coordinates to find the four neighboring texels around the sample position and compute the fractional horizontal and vertical offsets. Our eventual result is a blend of the 4 nearby texels, leading to a smoother result than nearest-neighbor sampling at the cost of added complexity.


The largest difference can be seen between the 1 sample per pixel nearest-neighbor vs bilinear sampling. In nearest sampling, we can clearly see more jagged white lines that mark longitude and latitude (ex: next to Brazil).

This is expected. Nearest-neighbor sampling chooses only one texel, so textures can look blocky or jagged. Bilinear sampling blends the four surrounding texels, producing much smoother transitions. The difference is especially noticeable for transitions between highly different colors, such as the transition from blue ocean color to the white latitude and longitude lines.

At 16 samples per pixel, both methods show smoother, more continuous lines. Averaging more samples reduces aliasing, so the difference between nearest and bilinear sampling is smaller.

Task 6: "Level Sampling" with mipmaps for texture mapping

Level sampling determines which texture resolution to use. Mipmaps store smaller, averaged versions of the original texture, which help reduce aliasing when many texels fit into one screen pixel. For implementation, we first calculate how much the UV coordinates change when moving one pixel in the x and y directions. Then we multiply these changes by the original texture's width and height and take the larger vector length, \(L\). We calculate the level as \(\log_2(\max(L,1))\), keeping it within the available mipmap levels.

For L_ZERO, we always use the original texture. For L_NEAREST, we round to the nearest level. For L_LINEAR, we sample the two surrounding levels and blend them based on the fractional part of the calculated level. Each level can use nearest or bilinear pixel sampling. Combining bilinear sampling with L_LINEAR gives trilinear filtering.

Nearest pixel sampling is cheap because it uses one texel, while bilinear sampling blends four for a smoother result without extra texture memory. Mipmaps use about 33% more texture memory for square textures, but reduce aliasing when the texture is shrunk. Linear level sampling samples twice as many texels to smooth transitions between levels. Supersampling smooths both triangle edges and textures, but the work and sample-buffer memory grow roughly with the number of samples per pixel.

In our images, L_ZERO with P_NEAREST shows jagged lines and unwanted patterns. Switching to P_LINEAR makes the transitions smoother. With L_NEAREST, fine details are averaged, but P_NEAREST still produces jagged edges within the texture. Using L_NEAREST with P_LINEAR gives smoother results, especially around the checkerboard and the center of the radial pattern, though some detail becomes blurry.
